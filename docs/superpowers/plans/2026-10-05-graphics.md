# Match graphics (sub-project G) — implementation plan

Spec: `docs/superpowers/specs/2026-10-05-graphics-design.md`. Spike: branch `spike/title-cards`
(`spikes/titlecard.ts`, `docs/superpowers/specs/2026-10-05-title-cards-spike.md`).

## Shape

Graphics are **optional and additive**. The engine keeps its `Cut[]` plan unchanged; graphics travel
next to it as `RenderOptions.graphics` (intro card, outro card, overlays tied to a cut index). This is a
deliberate deviation from the spec's "new cut kinds": `Cut` is shared with the preview plan, the reel
summary and many tests, and a side channel keeps a plain render byte-for-byte the same code path.

```
UI (RenderHighlights)            pure                               browser-only
 events, teams, settings ──► graphics/plan.ts ──► GraphicsSpec ──► graphics/painters.ts ──► render GraphicsPlan
                             graphics/layout.ts (DrawOps)          graphics/paint.ts, assets.ts
engine: mediabunnyEngine.ts ── render/nal.ts (pure bytes) ── render/segmentEncoder.ts (WebCodecs)
                            ── render/overlayWindow.ts (pure GOP window) ── render/yuvBlend.ts (pure pixels)
```

Splice rules from the spike, applied whenever at least one generated segment is in the reel:
1. VPS/SPS/PPS in-band on **every** key frame (footage from its own source's record, generated from
   the encoder's record).
2. Sample entry = the record whose SPS **covers** all others (coded size, DPB). None → graphics skipped.
3. Generated frames carry the footage `colorSpace`.

Plain renders (graphics off or all skipped) keep today's packet copy exactly, except the HEVC open-GOP
fix (task 9) if verification shows it is needed and safe.

Fallbacks: each graphic is prepared (encoded) before any of its packets reach the muxer, so a failure
skips just that graphic (copied footage instead / no card). Any error after muxing started with graphics
on → discard output and re-render plain. Every skip is reported through `onGraphics({ applied, skipped })`
and shown in the result panel.

Lower thirds are spliced by decoding the GOPs that overlap the overlay window (from the key before, so
open-GOP leading pictures decode), blending the overlay into the decoded **YUV planes** (no RGB round
trip for the footage pixels), re-encoding with key frames where the source had them, and resuming the
packet copy at the next source key (dropping its leading pictures, which were re-encoded).

## Out of scope / defaults

- Lower thirds: goals, own goals, penalties scored/missed, highlights with a note. Saves/fouls off.
- Cards 4 s, lower thirds 3 s, replay tag (off by default) for the length of the replay.
- Running score is computed locally (`graphics/plan.ts`); unify with H's `scoreAt` after both merge.

## Results (2026-10-05)

Media (native ffmpeg): `hevc.mp4` x265 hvc1 1920×1080 30000/1001, keyint 30 closed GOP, B-frames, full-range bt709
matrix (primaries/transfer untagged), AAC 48 kHz stereo tone; `lrv.mp4` x264 High 768×432 bt709 limited;
`hevc-opengop.mp4` x265 defaults (open GOP, untagged). Reel: VS card, goal (lower third 1–0), slowed replay,
highlight with note (lower third), goal (lower third 1–1), replay, FT card. Headless system Chrome, dev server 5183,
Intel i5-1038NG7 MacBook Pro 2020.

Joins found by mapping reel frames back to source frames: copy resumes at exactly the next source frame after
every re-encoded span. Frames at every graphic and just after every join (ffmpeg, AVFoundation) inspected.

Fallbacks verified in Chrome: no `VideoEncoder` → plain reel (bit-identical) + all five graphics listed with the
reason; `VideoDecoder.decode` throwing → cards kept, the three lower thirds skipped and listed.

Found and fixed on the way:
- HEVC open-GOP joins: ffmpeg dropped 4 frames and warned "non monotonically increasing dts" (also on main). Cut
  starts (CRA with leading pictures dropped) are now BLA_N_LP; all frames decode in order.
- Chrome's decoder returns limited-range NV12 for full-range HEVC, and VideoToolbox picks limited range for RGBA
  input. Decoded planes are range-converted and cards converted to YUV by us, so generated video carries the
  footage's range.

Deviations from the spec: graphics travel as `RenderOptions.graphics` next to the unchanged `Cut[]` (not new cut
kinds); team colour defaults unchanged (#f5f5f5 / #c2364a, ink chosen by luminance); persisted state version not bumped
(new keys have defaults).

Risks / untested: untagged footage gets bt709 primaries/transfer on generated segments (VideoToolbox fills them in;
WebCodecs cannot leave them unspecified), so ffmpeg-style pipelines (likely YouTube) reconvert copied footage after a
join — tagged GoPro-like footage is unaffected. Real GoPro files, Android/MediaCodec, YouTube, Safari/iPhone, phone
encode speed, 10-bit footage (lower thirds skipped: decoded format not 8-bit 4:2:0) and the whole-render plain retry
(no way to provoke a mid-mux failure from the page) are untested.
